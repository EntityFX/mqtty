# Анализ глубокого параллелирования MqttY (без ломки модели)

## Где сейчас параллелизм

| Фаза | Способ | Статус |
|------|--------|--------|
| RefreshTopology (сети → барьер → узлы → барьер) | TickWorkerPool, 12 воркеров, owned ranges | ✅ Есть, 7.6× wall на Relay |
| Construct (построение графа) | Серийно, ~0.05–0.2 с разово | Частично (memoize enum descriptions) |
| Connect / Subscribe | Серийно, один раз перед тиками | ❌ Не параллелится |
| PublishAll (публикации клиентов) | Серийно по брокерам и клиентам | ❌ Не параллелится |
| Counters / CounterClock | Серийно, на каждый тик | ❌ Не параллелится |
| Federation drain | Серийный цикл | ❌ Не параллелится |

## Глубокие гипотезы (вглубь BSP, без изменения порядка фаз)

### 1. Parallel Publish по брокерам (безопасно)
`PublishAll` делает `foreach broker → foreach client → Publish`. Брокеры находятся на разных сетях, их очереди независимы. Публикации разных брокеров в одном повторе не влияют друг на друга до следующего `RefreshTicks`.
- **Риск:** порядок пакетов между брокерами в общем сетевом пространстве может меняться, но так как сети не пересекаются (каждый брокер на своей сети), порядок между ними не влияет на доставку внутри сети.
- **Ожидаемый выигрыш:** PublishAll ≈ 10–15 % wall на dense конфигах.

### 2. Parallel Publish по клиентам внутри брокера (осторожно)
Клиенты одного брокера делят одну сеть и одну очередь. Меняя порядок публикаций между клиентами, можно изменить порядок пакетов в очереди сети → может изменить moment доставки.
- **Риск:** может изменить результаты симуляции (timing).
- **Вердикт:** только после валидации против golden trace.

### 3. Параллельный RefreshCounter / Counters (безопасно)
`_counters.Refresh` и `CounterClock.Publish` идут серийно в PublishClock. Счётчики независимы по группам.
- **Риск:** минимальный, counters не влияют на модель.
- **Ожидаемый выигрыш:** малый (<2 %), т.к. это не горячий путь тика.

### 4. Кэширование quiescence состояния узла (безопасно)
`ActiveOnly` проверяет `_outgoingQueueLength`, `_incommingQueueLength`, deferred списки каждого узла каждый тик. Для 8.7 млн вызовов `RefreshNode` это оверхед.
- **Идея:** помечать узел quiescent на N тиков подряд, пропускать проверку.
- **Риск:** если узел получает пакет в тике, когда мы пропускаем проверку — пакет потеряется.
- **Вердикт:** требует отслеживания входящих пакетов на уровне сети, сложно без ломки модели.

### 5. Один барьер вместо двух (небезопасно)
Сейчас: сети → барьер → узлы → барьер. Зависимость: узлы шлют пакеты в сети, которые должны быть обновлены в этом же тике. Убрать первый барьер можно только если узлы шлют в сети следующего тика — это меняет семантику модели.
- **Вердикт:** нельзя без изменения модели.

### 6. Пайплайнинг тиков (небезопасно)
Тик N+1 в фазе узлов, тик N+2 в фазе сетей. Меняет виртуальное время и порядок событий.
- **Вердикт:** нельзя без изменения модели.

### 7. Parallel Connect / Subscribe (безопасно, один раз)
Выполняются один раз перед тиками. Можно параллелить по брокерам.
- **Ожидаемый выигрыш:** разово, не влияет на тики.

## Результаты экспериментов (уже внесены в код)

### Parallel Publish по брокерам — ОТВЕРГНУТ как оптимизация по умолчанию, оставлен как opt-in

Реализовано как opt-in через `MQTTY_PARALLEL_PUBLISH=1` (выключено по умолчанию). Измерено на двух топологиях:

| Топология | seq | par | par+Parallel Publish | Вывод |
|-----------|-----|-----|---------------------|-------|
| 16 брокеров, 10 клиентов | 7801 ms | 2205 ms | 2213 ms | Никакого выигрыша (в шUME) |
| 64 брокера, 10 клиентов | 7939 ms | 2213 ms | 2213 ms | Никакого выигрыша |
| 64 брокера, 50 клиентов | 33649 ms | 10497 ms | 10599 ms | Никакого выигрыша |

**Причина:** PublishAll не является bottleneck — основное время тратится на refresh тиков (сети + узлы + барьеры), а не на публикацию. Contention на `TokenWindowAdmission._windowBytes` и `ConcurrentQueue.Enqueue` нивелирует выгоду от параллельной публикации даже на 64 брокерах.

**Вердикт:** код оставлен как opt-in (`MQTTY_PARALLEL_PUBLISH=1`) для будущих экспериментов на очень крупных топологиях, но не дает выигрыша на тестируемых конфигурациях.

### Кэширование quiescence-состояния узла — ЧАСТИЧНО

Применена безопасная микро-оптимизация в `Node.Refresh()`: дешевые проверки `List.Count` (деferred списки) перенесены перед дорогими `Volatile.Read` (очереди). Для простаивающих узлов все проверки всё равно равны нулю, поэтому выигрыш минимальный (в пределах шUME измерений).

Полное кэширование quiescence (пропуск проверки на N тиков) требует отслеживания входящих пакетов на уровне сети и пока не реализовано из-за риска потери пакетов.

2. **Отложить**: ActiveOnly, parallel clients, counters — на потом, после валидации против golden trace.
