### 3.3 Методические ограничения (указаны в статье §8, но не устранены)

1. **Только QoS 1, payload 16 байт.** Для QoS 0/2 коэффициенты другие (ожидаемо 2 и 8 пакетов на путь). Это существенно ограничивает обобщаемость моделей.
2. **Один семя (seed).** Измерения на одном хосте и одном семе; для научной публикации необходим мульти-сидовый прогон.
3. **Один хост.** Все измерения на Xeon E5-2680 v3; кроссплатформенная валидация только на Celeron N3350 (и то в отдельном файле `hardware-validation.csv`, не интегрированном в основную регрессию).
4. **Один получатель на backend в LB.** При нескольких подписчиках трафик умножается на fanout — не моделировано.
5. **Federation фиксирована star-топологией.** Ring и line представлены, но без глубокого анализа причин отклонений (holdout error 9.1 % для ring).

### 3.4 Что НЕ подтверждено (требует эксперимента)

- Утверждение *«Числа сообщений и сетевых пакетов совпадают с 12-ядерным Xeon»* (performance.md §2) для слабого хоста Celeron N3350 — косвенно подтверждается `hardware-validation.csv`, но не проверено перезапуском кампании.
- Benchmark-скорость (wall/refresh speedup) — не верифицирована в рамках этого анализа; требует длительных прогонов `Benchmark.Compare`.

## 4. Методика измерений производительности: критика

### 4.1 Сильные стороны

- **Постоянный пул воркеров** вместо `Task`/`Parallel.For` на каждый тик — правильное архитектурное решение.
- **Двухфазный refresh** с fence между сетями и узлами — корректная моделирование порядка фаз.
- **Spin/monitor auto-choice** барьера в зависимости от числа физических ядер — осознанное решение против SMT-переподписки.
- **Медиана из ≥ 5 прогонов**, чередование seq/par, прогрев ≥ 1 — соответствует хорошей практике бенчмаркинга.
- **Server GC + Concurrent GC=false** для бенчмарка и CLI — обосновано для детерминизма измерений.

### 4.2 Слабые стороны

| Проблема | Детали | Риск |
|----------|--------|------|
| Benchmark-числа с одного набора прогонов | Нет перезапуска для независимой верификации | Высокий — числа не могут быть воспроизведены читателем без запуска кампании |
| Нет confidence interval для speedup | Указаны только медианы, без стандартной ошибки или доверительных интервалов | Средний — невозможно оценить статистическую значимость различий |
| CV > 5 % — повторить Серию | Шум ±3–5 % на хосте, но порог не формализован в коде гейта | Средний |
| `diagnostics=differ` для Federation при recognised как pre-existing | Известное несоответствиеreceiver-латентности и queueDrops не устранено | Средний — Federation не детерминирован по этим метрикам |
| Federation drain ~45 % wall | Остаточный узкое место не закрыто, только 감소 от 3.74 до 3.19 с | Высокий — пределяет масштабируемость Federation |

### 4.3 Гейты: статус несоответствий

| Гейт | Критерий | Факт | Статус |
|------|----------|------|--------|
| G1 refresh ≥ 4× (8 физ.) | LB L 6.0×, Relay 6.3×, Fed 5.0–5.1×; LB ref 3.36× | LB ref не проходит | 🔴 |
| G2 wall ≥ 4× | LB L 4.98×, Relay 5.26×; Fed 4.1–4.2×; LB ref 2.98× | LB ref не проходит | 🔴 |
| G3 efficiency ≥ 50 % | LB L 42 %, Relay 44 %, Fed 33–35 % | Все не проходят | 🔴 |
| G4 seq == par | core match везде; Fed diagnostics differ | Fed diagnostics differ (pre-existing) | 🟡 |
| G5 масштабный ≥ 4× | LB L / Relay / Fed | На границе | 🟡 |
| G6 тесты | Integration 436/436, Web 62/62 | Подтверждено запуском | 🟢 |

1. **Нет фиксированных версий зависимостей для воспроизводства benchmarks.** `Benchmark.Compare` собирается под .NET 6/8, но точные версии NuGet-пакетов не зафиксированы в lock-файле для репродукции benchmark-чисел.

4. **Тесты Integration и Web нельзя запускать параллельно** (делят временные каталоги) — усложняет автоматизацию.

## 8. Рекомендации

### Критические (высокий приоритет)

1. **Провести независимую верификацию benchmark-чисел.** Запустить `Benchmark.Compare` с теми же параметрами и зафиксировать медианы с confidence intervals. Без этого числа остаются утверждениями на доверие.
2. **Устранить или документировать `diagnostics=differ` для Federation.** Если receiver-латентность и queueDrops не критичны для научных выводов — зафиксировать это явно; если критичны — исправить недетерминизм.
3. **Закрыть гейты G1–G3.** LB reference 2.98× wall и 3.36× refresh, а также efficiency 33–44 % — показывают, что параллельная версия не достигает целевых порогов для малых топологий. Это ограничение должно быть четко сформулировано в документации.

### Средний приоритет

4. **Обновить AGENTS.md:**
   - Добавить .NET 9.0.111 и 10.0.200 в список SDK (§3).
   - Добавить `EntityFX.MqttY.Experiment.Cli` в дерево структуры (§2).
   - Уточнить разделение между `EntityFX.MqttY.Cli` и `EntityFX.MqttY.Experiment.Cli`.
5. **Добавить confidence intervals к результатам бенчмарка.** Текущая подача только медиан не позволяет судить о статистической значимости speedup.
6. **Интегрировать гейты в CI.** Если G1–G6 являются условиями приёма, они должны проверяться автоматически.

### Низкий приоритет

7. **Расширить научную валидацию:** мульти-сидовый прогон, несколько хостов, QoS 0/2, несколько подписчиков на брокер.
8. **Добавить Docker-окружение** для воспроизводства измерений.

## 9. Заключение

Документация проекта MqttY **точно отражает архитектуру и реализацию** кода. Научная часть (`doc/analysis/message-scaling/`) содержит внутренне консистентные формулы, подтвержденные 63 измерениями в `measurements.csv` и коэффициентами регрессии в `results.json`.

Однако **научная обоснованность производительных чисел (benchmark speedup) не верифицирована независимо**, а методические ограничения (один семя, один хост, только QoS 1) снижают обобщаемость выводов. Гейты G1–G3 не закрыты для эталонных конфигураций.

**Общая оценка:** документация достоверна в описываемом, но требует уточнения справочных данных (SDK, структура проектов) и независимой верификации ключевых производительных утверждений перед использованием в научных публикациях или приёмочных испытаниях.
